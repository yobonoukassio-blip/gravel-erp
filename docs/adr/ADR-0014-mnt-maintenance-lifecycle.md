# ADR-0014 — MNT Maintenance Lifecycle

## Status

Draft — Phase 3 W0-P01. Date: 2026-05-13. Authors: Phase 3 planner + executor.

## Context

The maintenance module must track:
1. Preventive maintenance plans (interval-based: every N hours or N km).
2. Corrective work orders (breakdown repairs, emergency maintenance).
3. Spare parts consumption (deduction from spare_parts_stock).
4. Equipment availability metrics (MTBF, MTTR) for operational reporting.

The `production_equipment` entity from Phase 2 W1-P02 provides the equipment master.
Maintenance extends it with hour meter and odometer readings, plus links work orders
to equipment.

Key constraint: spare parts stock must never go negative (prevents ghost inventory).
This requires `SELECT FOR UPDATE` on the stock row before deduction.

## Decision

### Equipment extension

`production_equipment` is extended with:
- `hour_meter_current INT` — cumulative hours on the engine/hydraulic system.
- `odometer_km_current INT` — cumulative kilometers driven (for mobile equipment).

Both columns are nullable (not all equipment has both meters). Updated via `recordMeterReading()`
which validates that new reading >= current reading (meters don't go backward).

### work_order schema

A single `work_order` table covers both corrective and preventive maintenance:
- `work_order_type ENUM('CORRECTIVE', 'PREVENTIVE')` distinguishes the two.
- `pm_plan_id UUID NULL` — set when generated by a PM plan; null for spontaneous corrective.
- Status machine: `OPEN → IN_PROGRESS → CLOSED | CANCELLED`.

### Spare parts stock with SELECT FOR UPDATE

`WorkOrderService.consumePart(workOrderId, partId, quantity)` runs:
```sql
SELECT quantity_on_hand FROM spare_parts_stock
  WHERE id = $1 AND tenant_id = $2
  FOR UPDATE;
```
If `quantity_on_hand - quantity < 0`, throws `ERR_INSUFFICIENT_STOCK` (400).
Otherwise decrements the stock. This prevents concurrent deductions from racing
to negative stock.

### MTBF / MTTR computation

`WorkOrderService.close(workOrderId)` records `closed_at` and computes:
- `downtime_minutes` = `closed_at - opened_at` (for CORRECTIVE orders).

MTBF and MTTR are computed as rolling 12-month aggregates from `work_order.downtime_minutes`:
```
MTBF = (hours_of_uptime) / number_of_corrective_failures
MTTR = sum(downtime_minutes) / number_of_corrective_failures
```

Aggregates are materialized on `WorkOrderService.close()` into an `equipment_metrics` view
(or a periodic BullMQ job). Not a hypertable — maintenance events are rare (<<1/day per equipment).

### PM plan scheduling

`pm_plan` defines:
- `interval_hours INT` — generate WO every N hours.
- `interval_km INT` — generate WO every N km.
- `last_triggered_at_hours INT` — tracks the meter reading at last PM generation.

A scheduled BullMQ job (`PmPlanCheckJob`) runs daily and generates `work_order` rows
when `hour_meter_current - last_triggered_at_hours >= interval_hours`.

## Consequences

**Positive:**
- Single `work_order` table for both corrective and preventive avoids cross-table joins for availability metrics.
- `SELECT FOR UPDATE` is correct and simple for Phase 3 spare parts volume (<<1000 transactions/day).
- MTBF/MTTR computed at close time avoids expensive aggregate queries on the reporting dashboard.

**Negative:**
- `SELECT FOR UPDATE` requires transaction management — services must use `ds.transaction()`.
- Materialized metrics can drift if a work order is cancelled after being counted. Mitigated by
  recomputing the metric in the nightly drift detector job.

## Alternatives Considered

| Alternative | Why rejected |
|-------------|-------------|
| Separate tables for CORRECTIVE and PREVENTIVE | Split queries for availability metrics. Single table with type column is simpler. |
| Optimistic locking on spare_parts_stock | TOCTOU race condition under high concurrency. `SELECT FOR UPDATE` is deterministic. |
| Real-time MTBF from DB aggregation | Too expensive for dashboard polling. Pre-computed on close is the correct ERP pattern. |
| Skipping PM plan automation | Manual PM generation is error-prone. Automated generation from interval plan is required. |
